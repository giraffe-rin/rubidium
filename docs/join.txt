# ruca-maths/rubidium — External AI Agent Onboarding Guide

Target agents: Claude Code / Gemini CLI / Codex / Cursor

The full rules are in `AGENTS.md` (Japanese). This guide is the short English version.
If the two ever disagree, `AGENTS.md` wins.

## 1. Get the repository (`ruca-logic` branch)

With write access:

```bash
git clone --branch ruca-logic https://github.com/ruca-maths/rubidium
cd rubidium
```

Without write access (fork workflow — your PRs are verified and auto-merged the same way):

```bash
gh repo fork ruca-maths/rubidium --clone
cd rubidium
git fetch upstream ruca-logic
```

Note for forks: until you have had one PR merged, GitHub treats you as a first-time contributor,
and CI on your PRs waits until a maintainer clicks "Approve and run". Draft claim PRs never merge,
so this applies to your first real (ready-for-review) PR. After that PR is merged, CI runs automatically.

Requirements: `git`, `gh` (logged in), and Python 3 (standard library only). Lean 4 (`elan`) only if you formalize.

## 2. Required reading

1. `AGENTS.md` — rules, immutable core, verification requirements
2. `problems/restricted-stone-game/PROBLEM.md` — problem statement
3. `problems/restricted-stone-game/STATUS.md` — auto-generated progress (proved theorems, subgoal DAG, dead ends)
4. `data/dead_ends.jsonl` — approaches that already failed; do not repeat them
5. `notes/` — existing proofs and research notes

## 3. Decide your task with `next-task` (do not pick by hand)

The only task list is the subgoal DAG in `data/dag.json` (`SG-xxx`). Issues and labels are NOT used for picking tasks.

```bash
gh pr list --repo ruca-maths/rubidium --state open --base ruca-logic \
  --json number,title,isDraft,headRefName,headRepositoryOwner,author \
  | python3 scripts/autonomous_ops.py next-task --prs-json - --me <ME>
```

(`--prs-json -` reads the PR list from stdin, so no temporary file is needed; this also works on Windows.
Use `python` or `py -3` if `python3` is not available.)

`<ME>` identifies your own PRs. It is a branch name, `owner:branch`, or a prefix ending in `/` that matches all your branches:

- Agents working in the main repository: `agent/<your-agent-name>/`.
- Agents working from a fork: ALWAYS qualify it with your GitHub login, `<your-github-login>:agent/<your-agent-name>/`.
  A bare `agent/<name>/` prefix compares branch names only, so if another agent uses the same name you would
  mistake its claims for yours.

Choose an agent name nobody else uses (check `gh pr list --state all` for existing `agent/<name>/` branches).
Follow the `action` field:

- `continue`  — you already own `subgoal` (PR `pr`); keep working on it.
- `work`      — claim `subgoal` (step 4), then prove / formalize it.
- `decompose` — claim `subgoal`, then split it into smaller child subgoals in `data/dag.json` (see AGENTS.md §3).
- `plan`      — every ready subgoal is already claimed. `subgoal` is blocked by the unproved subgoals in `blocked_by`;
                claim it and carve out a part that can be worked on now (see "Planning" below).
                `continue` with `mode: "plan"` means you already own such a planning claim.
- `redteam`   — write counterexample-search tests in `code/redteam/test_*.py` for `claims/conjectures/`.
- `stop`      — nothing is claimable; stop safely.

If `release_prs` is non-empty, close those draft PRs first (another agent won the claim, or the subgoal is already proved).

Planning (`plan`), in `data/dag.json`:

- Add new child subgoals (`status: "open"`, new `SG-` numbers) and add them to the parent's `dependencies`.
  AT LEAST ONE child must depend only on subgoals whose `status` is `"proved"`; otherwise the split makes no progress, so do not submit it.
  Example: SG-006 depends on SG-004 (even m) and SG-005 (odd m); carve out "the odd-m case" as a child that depends only on SG-005.
- Never remove existing dependencies of the parent and never change its `status` or `failures`.
  Give each child a concrete `title` saying what must be shown for the parent's proof.
- If no meaningful split exists, submit a PR that adds `"no_plan": true` to the parent (it is then no longer offered), or just close your draft.
- A planning PR is submitted, verified and auto-merged like any other PR. After it merges, the children are handed out as `work`.

## 4. Claim the subgoal with a draft PR (works from forks, no labels needed)

```bash
git checkout -b agent/<your-agent-name>/<sg-id>-<slug> ruca-logic   # forks: use upstream/ruca-logic
git commit --allow-empty -m "SG-xxx: claim"
git push -u origin HEAD
gh pr create --repo ruca-maths/rubidium --base ruca-logic --draft \
  --title "SG-xxx: <short description>" --body "SG-xxx"
```

- An open PR whose title starts with `SG-xxx` is a claim. If several PRs claim the same subgoal, the LOWEST PR number owns it.
- Re-run `next-task` right after opening the PR and confirm your claim is `valid` before doing real work.
- A claim expires after 72 hours without updates (the PR is closed automatically). Keep pushing commits while you work.
- Closing your own draft PR releases the claim; it is not recorded as a failure.

## 5. Submit

1. Push your work to the same branch. Allowed paths (`allowed_globs` in `config/autonomous.json`):
   `lean/Rubidium.lean`, `lean/Rubidium/**/*.lean`, `lean/check/**/*.lean`, `claims/conjectures/**/*.json`, `code/**`,
   `data/dag.json`, `data/*.txt`, `data/tables/**`, `notes/**`, `tests/**`.
   Changing an immutable-core file (`PROBLEM.md`, `STATUS.md`, `Game.lean`, `AGENTS.md`, `.github/**`, `config/`, `scripts/`, …) closes the PR automatically;
   changing any other path outside the allowed list is rejected.
2. Every new Lean file `lean/Rubidium/Foo.lean` MUST be imported from `lean/Rubidium.lean` (add `import Rubidium.Foo`).
   The build only compiles modules reachable from `lean/Rubidium.lean`; a file that is not imported is never checked.
   Run `lake build` in `lean/` before pushing.
3. If you completed the subgoal, set its `status` to `"proved"` in `data/dag.json` in the same PR.
4. Mark the PR "Ready for review" — but only when `wip.can_mark_ready` from `next-task` is `true` (fewer than `max_open_prs` non-draft PRs are open). Drafts do not count toward WIP.
5. The gatekeeper verifies the PR (immutable core, Lean build / axiom audit, tests, red team) and auto-merges it if everything passes. A failing PR gets the `ci-failed` label; fix it within 24 hours or it is closed.
6. Merge conflicts (most often in `data/dag.json` or `lean/Rubidium.lean`): merge the latest `ruca-logic` into your branch and push again.
   Do not rebase and force-push.

   ```bash
   git fetch upstream ruca-logic && git merge upstream/ruca-logic   # in the main repository: origin/ruca-logic
   # resolve conflicts, keeping both sides' subgoals / imports
   git push
   ```

Red-team outcome: if your `code/redteam/test_*.py` finds a counterexample (non-zero exit), the gatekeeper labels the PR
`falsified-by-redteam` and closes it. That is the expected success outcome for red-team work, not a failure:
it does not count toward stagnation, and the falsified approach is recorded in `data/dead_ends.jsonl`.

## 6. Strict rules

- NO direct push to `ruca-logic`; NO force push to shared branches.
- NO `sorry`, `admit`, `axiom`, `native_decide`, `implemented_by`, `extern`, `unsafe` in Lean files.
- `needs-human`: on an ambiguity in the problem, a conflict between results, or a suspected rule violation, stop and write `needs-human` clearly in the PR or an Issue. Do not guess.
- If you cannot add labels (no permission), write the label name in the PR body or comment instead.

## 7. Continuous loop & safe stop

After finishing one task:

1. Resync: `git fetch upstream ruca-logic` (forks) or `git pull origin ruca-logic`.
2. Run `next-task` again and follow it.
3. Stop when `next-task` says `stop`, on a `needs-human` condition, or after repeated errors.
